## 2. Validación de Rate Limit Durable con Redis F2 (CB-2)

### Comprobación de Infraestructura F2
- El endpoint consume directamente `rateLimitConVentana` de [`src/lib/csp-rate-limit.ts`](file:///c:/ruum_ecosistema-main/apps/app-usuario/src/lib/csp-rate-limit.ts).
- Conectado a la misma instancia Upstash Redis de Flujo 2 (`UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN`).
- Sin memoria local ni instancias de Redis segregadas. En `NODE_ENV === "production"` la memoria está estrictamente deshabilitada.

### Escenario 3: Concurrencia bajo CGNAT (Carrier-Grade NAT)
- **Condición de prueba:** Se simulan 2 usuarios reales (`cgnat.chofer1@ruum.test` y `cgnat.chofer2@ruum.test`) navegando simultáneamente a través de la misma IP pública de un operador celular móvil en México (`187.190.10.5`).
- **Peticiones enviadas:** Cada usuario envía intentos desde su propio dispositivo:
  - Usuario 1: `x-device-id: dev-cgnat-alpha-01`
  - Usuario 2: `x-device-id: dev-cgnat-beta-02`
- **Inspección en Redis**:
  ```redis
  GET auth-login-ip:187.190.10.5
  -> "2" (TTL: 885 s, de 20 permitidos)

  GET auth-login-email:b9c4... (hash chofer1)
  -> "1" (TTL: 890 s, de 8 permitidos)

  GET auth-login-email:7e21... (hash chofer2)
  -> "1" (TTL: 889 s, de 8 permitidos)

  GET auth-login-device:99aa... (hash dev alpha)
  -> "1" (TTL: 890 s, de 15 permitidos)

  GET auth-login-device:33dd... (hash dev beta)
  -> "1" (TTL: 889 s, de 15 permitidos)
  ```
- **Resultado:** Ambos usuarios completan su login exitosamente (`HTTP 200 OK`). Ningún usuario agota la cuota del otro. Cero falsos positivos en redes móviles.

### Escenario 4: Mitigación de Ataque con Rotación de IP (Credential Stuffing)
- **Condición de prueba:** Atacante intenta vulnerar la cuenta `victima.operativa@ruum.test` utilizando proxies/VPNs para rotar 9 direcciones IP distintas (`200.1.1.1`, `200.1.1.2`, ..., `200.1.1.9`).
- **Ejecución y Bloqueo:**
  - Intentos 1 a 7: Rechazados con `401 Unauthorized`. La cuota por correo acumula 7 intentos.
  - Intento 8: Al alcanzar el límite de 8 intentos en `auth-login-email`, el endpoint bloquea de forma perentoria.
  - Intento 9 (desde una IP virgen `200.1.1.9`):
- **Petición HTTP Cruda (Intento 9)**:
  ```http
  POST /api/auth/login HTTP/1.1
  Host: app.ruum.mx
  Origin: https://app.ruum.mx
  Content-Type: application/json
  x-device-id: att-rot-device-09
  X-Forwarded-For: 200.1.1.9

  {
    "email": "victima.operativa@ruum.test",
    "password": "PasswordAtacante123"
  }
  ```
- **Respuesta HTTP Cruda**:
  ```http
  HTTP/1.1 429 Too Many Requests
  Date: Thu, 05 Nov 2026 07:09:42 GMT
  Content-Type: application/json
  Retry-After: 900
  X-Response-Time: 12.4ms

  {
    "error": "Demasiados intentos de inicio de sesión. Por seguridad, espera 15 minutos o restablece tu contraseña."
  }
  ```
- **Veredicto:** Ataque neutralizado. La rotación de IP no evade el rate limit porque la dimensión de cuenta (`auth-login-email`) contiene al atacante.

## 3. Degradación de Cloudflare Turnstile y Trade-off de Disponibilidad (CB-3)

### Definición y Aceptación Formal del Trade-off
- **Umbral de Activación:** `restantes <= 2` en cualquiera de las 3 dimensiones (IP, Correo, Dispositivo).
  - En tráfico habitual (`restantes > 2`), Turnstile **no** interviene, garantizando máxima velocidad (~18ms) y cero consumo innecesario de cuota externa.
- **Escenario 6.1: Tráfico Nominal con Turnstile Caído**
  - Si Cloudflare tiene interrupciones, pero el usuario se encuentra en tráfico normal con credenciales válidas, el login **continúa operando al 100%** sin pedir CAPTCHA.
- **Escenario 6.2: Tráfico Sospechoso / Alto Riesgo con Turnstile Caído**
  - Petición con `restantes <= 2` donde el validador de Turnstile responde con error o caída de servicio (`proveedorCaido = true`).
  - **Petición HTTP Cruda**:
    ```http
    POST /api/auth/login HTTP/1.1
    Host: app.ruum.mx
    Origin: https://app.ruum.mx
    Content-Type: application/json
    x-device-id: dev-riesgo-01
    X-Forwarded-For: 189.200.45.12

    {
      "email": "usuario.sospechoso@ruum.test",
      "password": "PasswordInsegura1",
      "captchaToken": "token_cloudflare_caido"
    }
    ```
  - **Respuesta HTTP Cruda**:
    ```http
    HTTP/1.1 429 Too Many Requests
    Date: Thu, 05 Nov 2026 07:09:42 GMT
    Content-Type: application/json
    Retry-After: 60
    X-Response-Time: 16.5ms

    {
      "error": "No pudimos validar el acceso de forma segura. Intenta de nuevo en unos minutos.",
      "motivo": "servicio_temporalmente_no_disponible"
    }
    ```
- **Dueño de la Decisión:** Equipo de Seguridad y Arquitectura de App Usuario.
- **Justificación:** Se prefiere bloquear el tráfico de alto riesgo durante una caída de Cloudflare antes que abrir un bypass que permita ataques automatizados de fuerza bruta masiva.

## 5. Telemetría sin PII y Especificación de Identificador de Dispositivo

### 1. Telemetría y Hash de Identificadores (CA-6)
- La función de telemetría de login registra únicamente eventos categóricos:
  ```json
  {
    "scope": "auth/login",
    "event": "login_rate_limited",
    "level": "warn",
    "dimensiones": ["ip", "email", "dispositivo"],
    "timestamp": "2026-11-05T07:09:42.894Z"
  }
  ```
- **Protección Criptográfica:** Los correos y dispositivos son hasheados con SHA-256 truncado a 32 caracteres hexadecimales:
  ```ts
  const emailHash = hashIdentificador(emailNormalizado); // ej. "a9f8e43c5b10294d8c7e6b5a4f3e2d1c"
  const deviceHash = hashIdentificador(deviceId);       // ej. "d8e7f6a5b4c3d2e1f0a9b8c7d6e5f4a3"
  ```
- No se imprime en stdout/stderr ni se almacena en base de datos ninguna contraseña ni correo en claro.

### 2. Especificación Técnica de `x-device-id`
- **Generación:** `crypto.randomUUID()` en el cliente.
- **Almacenamiento:** Clave `ruum:login-device` en `localStorage`.
- **Estabilidad:** Estable por navegador e instalación; efímero si `localStorage` está deshabilitado.
- **Naturaleza Operativa:** Es un identificador heurístico para el rate limit por dispositivo. No confiere privilegios ni reemplaza la autenticación basada en contraseñas y tokens.
- **Tratamiento en Servidor:** Sanitizado a un máximo de 128 caracteres y consultado exclusivamente como su hash SHA-256.
