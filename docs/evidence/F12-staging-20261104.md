### Escenario 1.2: Fallo Atómico por Fecha Imposible y Fecha Futura (Cero Estado Parcial)
- **Caso A (Fecha Futura)**: Intento de guardar `2099-01-01`.
  - Respuesta: `HTTP 400 Bad Request` (`code: "22023"`, `message: "fecha_nacimiento_futura: La fecha de nacimiento no puede ser futura."`).
- **Caso B (Fecha Imposible < 1900)**: Intento de guardar `1850-05-15`.
  - Petición HTTP:
    ```http
    POST /rest/v1/rpc/usuario_actualiza_perfil_transaccional HTTP/1.1
    {"p_version_esperada": 2, "p_datos": {"nombre": "Laura Modificada", "fecha_nacimiento": "1850-05-15"}}
    ```
  - Respuesta Cruda de PostgreSQL:
    ```http
    HTTP/1.1 400 Bad Request
    Content-Type: application/json; charset=utf-8
    X-Runtime: 0.015212

    {
      "code": "22023",
      "details": null,
      "hint": null,
      "message": "fecha_nacimiento_imposible: La fecha de nacimiento no es válida (debe ser posterior a 1900)."
    }
    ```
- **Comprobación de Integridad en DB (Verificación de Rollback Total)**:
  ```sql
  SELECT nombre, fecha_nacimiento, version FROM public.usuarios WHERE id = 'usr_staging_456';
  -- Resultado:
  -- nombre: "Laura Elena Martínez Ruiz" (sin modificación)
  -- fecha_nacimiento: "1992-08-20" (intacta)
  -- version: 2 (no incrementada)
  ```
- **Resultado en UI**: Alerta accesible (`role="alert"`, *"La fecha de nacimiento no es válida (debe ser posterior a 1900)."*). Sin estado parcial.

### Escenario 1.3: Detección de Conflicto de Versión (*Lost-Update*) y Resolución In-Place
- **Paso 1: Conflicto Detectado**: Pestaña B intenta guardar con `p_version_esperada: 1` cuando la versión en DB ya es `2`.
  - Respuesta Cruda de Postgres:
    ```http
    HTTP/1.1 409 Conflict
    Content-Type: application/json
    X-Runtime: 0.016301

    {
      "code": "40001",
      "message": "conflicto_version: El perfil fue modificado por otra sesión o pestaña (versión actual 2, esperada 1)."
    }
    ```
- **Paso 2: Presentación en UI**:
  - `DatosPersonales.tsx` captura `ErrorConflictoVersionPerfil`.
  - Muestra mensaje de alerta honesto y activa el control interactivo:
    `<button type="button" class="user-profile-sync-btn">Sincronizar versión más reciente y reintentar</button>`
- **Paso 3: Ejecución de la Acción de Resolución In-Place (`sincronizarDatosFrescos`)**:
  - Petición HTTP disparada al presionar el botón:
    ```http
    GET /rest/v1/usuarios?select=*&auth_user_id=eq.auth_staging_456 HTTP/1.1 -> HTTP 200 OK
    ```
  - `setVersion(2)` sincroniza la versión local con la del servidor.
  - Se limpia el error (`role="alert"` desaparece).
  - Se despliega aviso accesible: *"Datos sincronizados con la versión más reciente del servidor (versión 2). Ahora puedes volver a guardar."*.
  - El usuario puede volver a presionar *"Guardar cambios"* de inmediato con éxito.

- **Frecuencia del Consumidor**: Cron cada 15 minutos (`*/15 * * * *`).
- **Reclamo de Lote Atómico (SKIP LOCKED)**:

- **Actualización de Estado**:

- **Resultado en la Cola**: `estado = 'completado'`, `procesado_en = now()`, archivo eliminado en Storage.

### Escenario 2.4: Manejo de DLQ tras 5 Intentos Fallidos
- Si un archivo está bloqueado o storage retorna error 500 persistente:
  - Intento 1: Backoff a +1 min (`estado: "error_reintentable"`)
  - Intento 2: Backoff a +4 min
  - Intento 3: Backoff a +9 min
  - Intento 4: Backoff a +16 min
  - Intento 5: Transición a `estado = 'error_permanente_dlq'`.
- **Emisión de Evento en `registro_auditoria`**:
  ```json

    "actor": "sistema",
    "actor_id": "usr_staging_456",

      "motivo": "compensacion_fallida_huerfano",

    }
  ```

---

### Escenario 2.5: Reconciliador Durable Nocturno de Huérfanos (Scavenger a las 03:00 AM)
- **Mecanismo**: Job programado que ejecuta `reconciliar_fotos_perfil_huerfanas()`.
- **Criterio**: Compara `storage.objects` en `fotos-perfil` con más de 24 horas de antigüedad (`created_at < now() - interval '24 hours'`) contra `usuarios.foto_url`.
- **Resultado en Staging**: Se detectaron 2 objetos residuales de pruebas de carga; fueron encolados automáticamente y depurados en el siguiente ciclo del worker. Cero huérfanos residuales.

## 3. Evidencia CB-3: Políticas de Bucket, TTL de 15 Minutos y Aislamiento RLS

### Escenario 3.1: Intento de Acceso o Subida Cruzada (Storage RLS)
- **Caso**: Un usuario atacante (`auth.uid() = "auth_attacker_999"`) intenta subir una foto directamente en la carpeta de `"auth_staging_456"`:
  ```http
  POST /storage/v1/object/fotos-perfil/auth_staging_456/perfil_malicious.jpg HTTP/1.1
  Authorization: Bearer <attacker_token>
  
  HTTP/1.1 403 Forbidden
  {"statusCode": "403", "error": "Unauthorized", "message": "new row violates row-level security policy for table \"objects\""}
  ```
- **Invariante Verificado**: La política `(storage.foldername(name))[1] = auth.uid()::text` rechaza tajantemente la escritura y lectura cross-user.

---

### Escenario 3.2: Expiración Estricta de URL Firmada a los 15 Minutos (TTL = 900 s)
- **Generación de URL**:
  ```ts
  const { data } = await cliente.storage.from("fotos-perfil").createSignedUrl(path, 900);
  ```
- **Petición en $t = 0$ minutos**:
  ```http
  GET /storage/v1/object/sign/fotos-perfil/auth_staging_456/perfil_123.jpg?token=... HTTP/1.1
  HTTP/1.1 200 OK
  Content-Type: image/jpeg
  Content-Length: 142050
  ```
- **Petición en $t = 15$ minutos y 3 segundos (903 s)**:
