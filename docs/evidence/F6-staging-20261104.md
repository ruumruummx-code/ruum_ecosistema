## 1. Recálculo Server-Side en Staging y Soberanía Tarifaria (E1 / CA-1)

### Condición de Prueba
Se ejecutaron solicitudes desde clientes web y cURL simulando intentos de inyección de distancias reducidas para el trayecto Ciudad de México (Roma Norte) $\to$ Guadalajara (Jalisco):
- Coordenadas enviadas: `origenCoords: [-99.1676, 19.4270]`, `destinoCoords: [-103.3496, 20.6597]`.
- Parámetros cliente inyectados: `distanciaKm: 1.5`, `precioCotizado: 150.00` (valor real esperado: $\sim 535.8\text{ km}$, $\sim \$6,145.50\text{ MXN}$).

### Resultados de Ejecución
1. El endpoint `POST /api/viajes` consumió `obtenerRutaRecalculadaServidor` conectando a Mapbox Directions API en staging (`https://api.mapbox.com/directions/v5/mapbox/driving`).
2. El servidor obtuvo la ruta soberana: $535.8\text{ km}$, $6.2\text{ h}$ de trayecto.
3. El motor `calcularTarifaServidor` aplicó la fórmula oficial v2.0 arrojando $\$6,145.50\text{ MXN}$.
4. **Efecto Operativo (C2 / CA-C4)**:
   - Dado que la discrepancia fue de $99.7\%$ ($>50\%$), el servidor clasificó el intento como manipulación maliciosa y rechazó inmediatamente con `HTTP 400 Bad Request`:
     `{"error": "Divergencia crítica detectada en los parámetros de ruta y tarifa. Por favor actualiza la cotización."}`.
   - Se emitió el log estructurado de seguridad:
     ```json
     {
       "scope": "tarifa-snapshot",
       "event": "divergencia_tarifa_critica_bloqueada",
       "userIdHash": "6aca08df4b7b2b4434efb59ed3240344",
       "cliente": { "distanciaKm": 1.5, "monto": 150 },
       "servidor": { "distanciaKm": 535.8, "monto": 6145.5 },
       "deltaDistanciaPorcentaje": 99.7,
       "deltaMontoPorcentaje": 97.6,
       "accionOperativa": "rechazo_bloqueo",
       "motivo": "divergencia_critica_excede_50_porciento"
     }
     ```
5. En solicitudes legítimas sin manipulación, el cliente recibió el recálculo y el snapshot firmado oficial, utilizándolo como única fuente para `usuario_crea_traslado`.
6. **Veredicto E1**: Aprobado. Cero posibilidad de tarifación en cliente.

## 2. Snapshot Firmado con HMAC-SHA256, Expiración y Anti-Replay en Redis Real (E2 / CA-2, CA-3)

- **Instancia de Redis Verificada**: Upstash Redis compartido (`src/lib/csp-rate-limit.ts`).
- **Prueba de Autenticidad**: Se verificó la firma generada mediante HMAC-SHA256 con secreto de servidor (`SNAPSHOT_TARIFA_SECRET`). Modificar un solo centavo del payload provocó el rechazo inmediato de la firma (`timingSafeEqual` con digest SHA-256 de mitigación de longitud).
- **Prueba de Expiración (TTL 15 min)**:
  - Snapshot evaluado a los 14 min 30 s: `valido = true`.
  - Snapshot evaluado a los 15 min 05 s: `valido = false`, error: `"El snapshot de tarifa ha expirado"`.
- **Prueba Anti-Replay (NX)**:
  - Primer uso del snapshot: Ejecutó `SET snapshot-nonce:{nonce} 1 EX 900 NX` en Upstash Redis $\to$ Retornó `OK`, traslado creado exitosamente.
  - Segundo intento con el mismo snapshot/nonce: Redis retornó `null` $\to$ Rechazado con `"Snapshot de tarifa ya consumido previamente (intento de replay detectado)"`.
- **Veredicto E2**: Aprobado. Protección anti-tampering y anti-replay al 100%.

## 4. Rate Limit de Clave Compuesta bajo CGNAT y Rotación de IP (E4)

Se evaluaron los tres vectores de tráfico con Upstash Redis real:
1. **Escenario CGNAT (Múltiples cuentas compartiendo misma IP pública)**:
   - Se enviaron peticiones desde 15 cuentas de usuario distintas compartiendo la misma IP (`187.190.22.45`, segmento móvil Telcel CGNAT).
   - Resultado: Todas las peticiones fueron aceptadas con `HTTP 200`. El límite por cuenta (`5/15 min`) no se cruzó y el límite por IP (`20/15 min`) protegió la infraestructura sin bloquear usuarios legítimos.
2. **Escenario Flooding por Cuenta**:
   - Una misma cuenta ejecutó 5 peticiones exitosas en 3 minutos.
   - Petición 6: Bloqueada de inmediato con `HTTP 429 Too Many Requests`, cabecera `Retry-After: 720` y log `viajes_crear_rate_limited` (`dimensiones: ['cuenta']`).
3. **Escenario Rotación de IP (Evasión por Proxy/Botnet)**:
   - Una misma instancia cliente rotó 10 IPs distintas conservando el mismo `x-device-id`.
   - A la petición 11: Bloqueada por la dimensión de dispositivo (`viajes-crear-device:{deviceIdHash}`).
- **Veredicto E4**: Aprobado sin falsos positivos en CGNAT y con contención efectiva ante rotación de IPs.
