1. Fortalezas — Lo que funciona bien
Skip-link de accesibilidad implementado correctamente en el layout raíz.
Uso consistente de aria-live="polite" en la tarjeta de traslado activo.
Touch targets mínimos de 44px definidos en globals.css y aplicados a todos los controles.
Arquitectura mobile-first estricta: 100dvh con soporte Safari/PWA.
Design System V2 bien documentado con tokens semánticos coherentes.
Dark mode completo con contraste ACC-8 auditado y corregido en tokens.
LiveRegion global para anuncios de accesibilidad a lectores de pantalla.
Validación de formulario inline con foco programático en primer error.
Gestos de arrastre en bottom sheets con manejo correcto de pointer capture.
Safe-area-inset en todos los elementos fijos (nav, wizard actions, header).

2. Navegación y Arquitectura de Información
N1
Colores de indicador activo no son coherentes entre pestañas
El componente NavegacionUsuario utiliza tres valores hardcodeados distintos para el indicador activo: #00D1D1 en Inicio, #0046c4 en Traslados, #0066FF en Carga Masiva. El sistema de diseño tiene tokens semánticos disponibles que no se usan aquí.
Alto
Archivo: NavegacionUsuario.tsx:199–210
Impacto: El usuario percibe la navegación inferior como visualmente inconsistente; el teal de inicio no comunica el mismo "activo" que el azul de traslados.
Recomendación: Unificar con var(--user-color-brand) como color único de estado activo, o documentar formalmente la intención semántica de cada color como parte del spec de navegación.
N2
Ítem "Carga Masiva" en navegación principal puede confundir al usuario promedio
Los 4 ítems del bottom nav son: Inicio, Traslados, Carga Masiva, Cuenta. "Carga Masiva" es una función de negocio avanzada (flotillas/lotes) que no aplica a usuarios individuales. Su presencia permanente aumenta la carga cognitiva para el 80% de usuarios que nunca la usarán.
Alto
Archivo: NavegacionUsuario.tsx:68–73 (DESTINOS constant)
Recomendación: Mostrar "Carga Masiva" solo si el usuario tiene el rol/flag de empresa activo, o moverlo a un acceso dentro de "Cuenta". El espacio liberado podría usarse para "Solicitar" como CTA directa.
N3
Título de sección secundaria generado con cadena de condicionales difícil de mantener
El appbar de pantallas secundarias (Cuenta, Preferencias, etc.) se construye con una cadena tituloSecundario = pathname === "..." ? "..." : null de 6 rutas. Si se agrega una ruta nueva sin actualizar este bloque, la pantalla mostrará "Hola" como título en vez del nombre de la sección.
Medio
Archivo: NavegacionUsuario.tsx:151
Recomendación: Mover la lógica de título a un mapa de configuración o permitir que cada página exponga su título via metadata/context, eliminando la dependencia implícita.
N4
El FAB "Solicitar traslado" se oculta en demasiadas condiciones no documentadas
El botón flotante de acción está oculto en 5 rutas distintas usando negaciones encadenadas. La lógica es difícil de auditar visualmente y puede resultar en pantallas donde el CTA principal desaparece inesperadamente para el usuario.
Medio
Archivo: NavegacionUsuario.tsx:243
Recomendación: Invertir la lógica a una lista blanca explícita de rutas donde el FAB sí debe aparecer, en lugar de una lista negra de exclusiones.

3. Pantalla de Inicio (Dashboard)
I1
El texto del empty state es poco motivador y no informa el valor diferencial
Cuando no hay traslados activos, el texto dice: "No tienes traslados activos. Solicita tu primer traslado y sigue cada etapa en tiempo real con evidencia fotográfica." La frase es funcional pero no conecta emocionalmente. La ilustración SVG es genérica y de bajo contraste.
Medio
Archivo: InicioMobile.tsx:242–262
Recomendación: Añadir un subtexto del tipo "Tu vehículo, protegido desde la llave hasta la entrega" y mostrar al menos un punto de valor (seguridad, evidencia, conductor verificado). Considerar una ilustración más relevante o con identidad de marca más fuerte.
I2
El acceso rápido "Mis vehículos" muestra el conteo pero no es accionable cuando hay 0
El card de acceso rápido "Mis vehículos — 0 registrados" navega a /cuenta/vehiculos, pero no diferencia si el 0 es porque nunca registró ninguno (deberían añadir uno) o porque se borraron. No hay CTA ni tooltip educativo para el estado vacío.
Medio
Archivo: InicioMobile.tsx:269–279
Recomendación: Cuando vehiculos.length === 0, el subtexto debería decir "Registra tu primer vehículo" con un estilo ligeramente diferenciado para indicar que es un primer paso recomendado.
I3
El stepper de progreso no tiene estados visuales diferenciados para "en tránsito activo" vs "completado"
Los items del stepper usan clases is-complete, is-current e is-pending. El estado is-current no tiene una animación de pulso u otro indicador visual de actividad en tiempo real cuando el traslado está en curso.
Bajo
Archivo: InicioMobile.tsx:132–153 / InicioUsuario.css
Recomendación: Añadir una animación de pulso sutil (@keyframes pulse) al punto de etapa activa cuando viaje.estado === "traslado_en_curso", respetando prefers-reduced-motion.
I4
Dashboard desktop carga InicioMobile en vez de InicioDesktop por defecto
El componente InicioUsuario siempre renderiza InicioMobile. El desktop solo se activa si el consumidor importa InicioDesktop explícitamente. Si la página raíz utiliza InicioUsuario, el escritorio recibe la versión móvil hasta que un media query lo reemplaza en cliente.
Medio
Archivo: InicioUsuario.tsx:9–11
Recomendación: Revisar el page.tsx de inicio para confirmar que el servidor ya elige entre Mobile/Desktop via ContenidoResponsivePersistente u otro mecanismo responsivo correcto. Documentar este patrón explícitamente para evitar regresiones.

4. Flujo de Autenticación
A1
Selector de idioma en login es UX noise sin funcionalidad real documentada
El componente LoginCliente incluye estado idioma: "ES" | "EN" y un menú de selección de idioma. Sin embargo, toda la interfaz permanece en español independientemente del idioma seleccionado. Esto crea una expectativa falsa que puede confundir o frustrar a usuarios anglófonos.
Alto
Archivo: LoginCliente.tsx:283–284
Impacto: Mina la confianza cuando el usuario selecciona "EN" y nada cambia. Puede ser reportado como bug.
Recomendación: Eliminar el selector de idioma hasta que la internacionalización esté implementada, o implementar i18n mínimo con next-intl para las rutas de autenticación.
A2
El mensaje de error de contraseña es demasiado escueto
El error de contraseña vacía es solo "Introduce tu contraseña." No se da ninguna pista sobre requisitos de complejidad en el flujo de registro (longitud mínima, caracteres especiales, etc.), lo que obliga al usuario a fallar primero para descubrirlos.
Medio
Archivo: LoginCliente.tsx:294
Recomendación: En el flujo de registro, mostrar los requisitos de contraseña de forma proactiva con indicadores de cumplimiento en tiempo real. En login, el error puede simplificarse a "Contraseña incorrecta" (cuando falla la autenticación) vs "Campo requerido".
A3
El botón "Omitir" del onboarding lleva a /login, no a /registro
En la pantalla de onboarding, tanto "Omitir" como el link final "Ya tengo una cuenta" apuntan a /login. El CTA principal del último paso es "Crear cuenta y cotizar" → /registro. Si el usuario aterriza en onboarding sin cuenta, el botón de omitir debería ofrecer ambas opciones.
Bajo
Archivo: onboarding/page.tsx:113
Recomendación: Cambiar el texto "Omitir" a "Acceder" o mostrar dos acciones: "Ya tengo cuenta" y "Crear cuenta", para no forzar al nuevo usuario a ir a login cuando realmente necesita registro.

5. Flujo de Solicitud de Traslado (Wizard)
T1
La barrera de verificación bloquea sin mostrar qué falta exactamente
Cuando t.bloqueoVerificacion está activo, se muestra el texto del bloqueo vía <Aviso tono="atencion">{t.bloqueoVerificacion}</Aviso>. El usuario ve solo un mensaje de aviso sin una lista clara de documentos pendientes, porcentaje de completitud ni pasos específicos para desbloquear el flujo.
Crítico
Archivo: NuevoTrasladoForm.tsx:88–121
Impacto: Puede causar abandono del flujo. El usuario no sabe qué verificar ni cuánto tiempo tomará.
Recomendación: Mostrar un checklist de pasos de verificación (INE, comprobante, etc.) con estado de cada uno. Incluir tiempo estimado de revisión. Ofrecer "Notificarme cuando esté listo" si la revisión está en curso.
T2
El dialog de selección de ubicación tiene UX deficiente en móvil
El SeleccionUbicacionInicial es un <dialog> centrado con clase m-auto, pero en móvil esto hace que el teclado virtual lo empuje y sea parcialmente ilegible. La lista de sugerencias tiene max-h-64 overflow-y-auto, pero en dispositivos pequeños con el teclado abierto apenas caben 1-2 resultados.
Alto
Archivo: NuevoTrasladoForm.tsx:24–33
Recomendación: Convertir este dialog en un bottom sheet que ocupa el 90% de la pantalla desde la parte inferior, evitando conflictos con el teclado virtual. Usar position: fixed; inset-block-end: 0.
T3
Sin indicador de progreso visible en el wizard mobile
El CotizadorPortal maneja pasos (Ruta, Vehículo, Detalles, Tarifa, Pago) pero no hay un indicador de progreso visible para el usuario móvil que indique en qué paso está y cuántos faltan. Solo el heading del paso cambia.
Alto
Archivos: CotizadorPortal.tsx / PasoRuta.tsx, PasoVehiculo.tsx, etc.
Recomendación: Añadir una barra de progreso de pasos (step indicator) en el user-wizard-actions superior. Modelo: "2 de 5 — Vehículo" con puntos o barra de progreso.
T4
La tarifa cambiada se maneja con scroll programático pero sin confirmación de contexto suficiente
Cuando la tarifa previa se invalida (C-02), se hace scroll al aviso y se enfoca el botón. Sin embargo, el aviso no explica por qué cambió la tarifa (distancia, horario, disponibilidad), lo que puede generar desconfianza o percepción de "bait and switch".
Medio
Archivo: NuevoTrasladoForm.tsx:64–82
Recomendación: El aviso de tarifa actualizada debe incluir: precio anterior tachado, precio nuevo en verde/azul, y una línea de motivo ("El precio fue recalculado por disponibilidad de conductores").

6. Pantalla "Mis Traslados"
M1
5 pestañas de filtrado son demasiadas para el espacio disponible en móvil
Las pestañas: Activos, Programados, Finalizados, Cancelados, En revisión — en pantallas de 360px generan un scrollable tablist horizontal con texto truncado. Las pestañas menos usadas (En revisión) ocupan el mismo peso visual que Activos.
Medio
Archivo: MisViajesCliente.tsx:284–290
Recomendación: Reducir a 3 pestañas primarias: Activos, Historial, Pendientes. "Cancelados" y "En revisión" pueden ser filtros dentro de Historial. Esto reduce el tiempo de decisión del usuario (Ley de Hick).
M2
El filtro de búsqueda y el de fecha/tipo están en un bottom sheet pero la apertura no tiene animación de entrada
El panel de filtros usa MobileBottomSheet que tiene soporte para gestos y cierre, pero no hay animación de entrada documentada en el CSS del módulo. La aparición abrupta puede ser percibida como un salto visual.
Bajo
Archivos: MisViajesCliente.tsx / mobile-bottom-sheet.module.css
Recomendación: Verificar que el bottom sheet tenga transform: translateY(100%) → translateY(0) como transición de entrada, respetando prefers-reduced-motion.
M3
Empty state sin distinción entre "no hay traslados aún" vs "sin resultados para tu búsqueda"
El componente FichaVacia recibe hayBusqueda y hayFiltro, pero el copy del empty state de "sin filtro" dice genéricamente "No hay traslados" sin un CTA claro para solicitar el primer traslado.
Medio
Archivo: MisViajesCliente.tsx:220–284
Recomendación: Para el estado "sin traslados jamás" en pestaña Activos, mostrar un CTA prominente "Solicitar mi primer traslado" con el mismo estilo que el botón primario del wizard.

7. Pantalla de Cuenta
C1
Colores hardcodeados en la tarjeta de perfil no respetan el Design System V2
La tarjeta superior de perfil usa bg-[#0c2340], text-white, border-white/20 en vez de las variables del scope user-v2-scope. El dark mode tiene un override adicional dark:bg-[#081a2e] que duplica lógica ya manejada por los tokens semánticos.
Alto
Archivo: CuentaCliente.tsx:316
Recomendación: Migrar a var(--user-color-primary) como fondo, var(--user-color-on-action) para texto, usando la clase user-v2-scope. Eliminar las utilidades Tailwind de color directo en este componente.
C2
El submenú de "Cuenta" usa aria-haspopup="dialog" pero el bottom sheet no restaura el foco al cerrar
El botón de sección (aria-haspopup="dialog") abre la HojaCuenta que es un <dialog>. Al cerrar vía "Cerrar" o click fuera, el foco debería volver al botón que abrió el dialog. El patrón useDialogAccesible maneja esto con focoInicial, pero no está configurado el retorno de foco al trigger original.
Medio
Archivo: CuentaCliente.tsx:137–211
Recomendación: Pasar la referencia del botón activador como focoAlCerrar a useDialogAccesible, o gestionar el retorno de foco manualmente en la función cerrarHoja.
C3
La ilustración de ciudad inferior es decorativa pura pero ocupa espacio valioso en pantallas cortas
La ilustración SVG IlustracionCiudadInferior se muestra siempre al final de la pantalla de cuenta. En dispositivos con pantallas de 568px o menos con el scroll activo, desplaza el contenido y puede requerir scroll adicional innecesario.
Bajo
Archivo: CuentaCliente.tsx:490
Recomendación: Ocultar esta ilustración en pantallas con altura de viewport menor a 700px usando @media (max-height: 700px), o aplicar un max-height menor para reducir su footprint.

8. Accesibilidad (WCAG 2.1 AA)
Ac1
El progressbar del onboarding tiene atributos ARIA incorrectos
El indicador de pasos usa role="progressbar" en un <div> que contiene <button>s. Un progressbar no debe ser interactivo (ARIA spec). Los botones de navegación de pasos deberían ser parte de un role="tablist", no de un progressbar.
Crítico
Archivo: onboarding/page.tsx:132–152
Impacto WCAG: 4.1.2 — Componentes interactivos deben tener el nombre, rol y valor correctamente expuestos a tecnologías asistivas.
Recomendación: Separar: usar un <ol aria-label="Pasos del recorrido"> con role="tab" para los botones, y un <progress> visual solo. O simplificar con dots de navegación simples con aria-current="step".
Ac2
Los íconos SVG inline del dashboard desktop no tienen texto alternativo adecuado
En InicioDesktop.tsx, muchos íconos son rendereados como <Icon name="pin" /> sin texto visible. Si el componente DashboardIcon no provee un aria-label o aria-hidden apropiado, los lectores de pantalla anuncian "svg" o contenido sin contexto.
Alto
Archivo: InicioDesktop.tsx / dashboard/DashboardIcon.tsx
Recomendación: Auditar DashboardIcon para confirmar que todos los íconos decorativos tienen aria-hidden="true" y los íconos funcionales tienen aria-label explícito o están dentro de un elemento con texto accesible.
Ac3
El campo de búsqueda de dirección en el wizard carece de role="combobox" y asociación con la lista
El AutocompletarDireccion presenta un <input> y una <ul> de sugerencias, pero si no implementa correctamente role="combobox", aria-expanded, aria-owns y aria-activedescendant, los usuarios de lector de pantalla no sabrán que hay sugerencias disponibles.
Alto
Archivo: viajes/nuevo/components/AutocompletarDireccion.tsx
Recomendación: Implementar el patrón ARIA Combobox completo: role="combobox" en el input, aria-expanded, y role="listbox" / role="option" en las sugerencias. Verificar navegación con teclas de flecha.
Ac4
Contraste de texto muted sobre fondos de surface en modo claro podría fallar en ciertos contextos
El token --user-color-muted: #4e5f80 sobre --user-color-surface-soft: #eff4fa tiene una relación de contraste de ~4.8:1. Aunque supera el mínimo de 4.5:1 para texto normal, los textos de 12px o menores requieren 7:1 (nivel AAA). Varios componentes usan este color en textos de 11–12px.
Medio
Archivos: globals.css:559
Recomendación: Para textos ≤13px, usar un token más oscuro como #3d4f6e (≥5.5:1). Aplicar la corrección ya existente del ACC-8 consistentemente en todos los tamaños tipográficos pequeños.
Ac5
El stepper de traslado activo usa aria-current="step" pero sin descripción del estado previo/siguiente
Los items del stepper en InicioMobile y InicioDesktop tienen aria-current="step" en el paso actual, pero un usuario de screen reader no recibe información de cuántos pasos hay en total ni cuáles están completados vs pendientes de forma anunciada.
Medio
Archivos: InicioMobile.tsx:132–153
Recomendación: Añadir al <ol> un aria-label="Progreso del traslado: paso X de 3" dinámico, y en cada <li> un aria-label completo como "Recolección: Completada" o "En tránsito: Paso actual".

9. Consistencia Visual y Design System
V1
Mezcla de estrategias de estilado: CSS Modules, Tailwind utilities y clases BEM personalizadas en el mismo componente
En InicioDesktop.tsx se usan styles.xxx (CSS Module), mientras que en CuentaCliente.tsx se usan clases Tailwind puras con valores hardcoded. En NavegacionUsuario.tsx se mezclan clases user-v2-xxx con utilidades Tailwind directas. La ausencia de una estrategia unificada dificulta la consistencia y el mantenimiento.
Alto
Recomendación: Definir una guía de estilo explícita: componentes "first-party" de UI deben usar el Design System V2 (user-v2-*), Tailwind solo para utilidades de layout, y CSS Modules únicamente para animaciones o estilos complejos no expresables con el sistema.
V2
Radio de borde inconsistente en las tarjetas de cuenta
La tarjeta de perfil usa rounded-[24px], las tarjetas de menú usan rounded-2xl (16px), y el banner de estado de conductor usa rounded-2xl. El token del sistema es --user-radius-card: 16px. La tarjeta de perfil al usar 24px es inconsistente con el sistema.
Medio
Archivo: CuentaCliente.tsx:316
Recomendación: Alinear a var(--user-radius-card) o definir un token adicional --user-radius-card-hero: 20px si la tarjeta de perfil necesita diferenciarse intencionalmente.
V3
La tipografía del nombre de usuario en Cuenta usa uppercase lo que dificulta la lectura de nombres propios
La clase uppercase tracking-tight en el nombre del usuario en la tarjeta de perfil (h2) transforma "María González" en "MARÍA GONZÁLEZ". Los nombres propios en mayúsculas son más difíciles de leer y pueden parecer agresivos o impersonales.
Medio
Archivo: CuentaCliente.tsx:340
Recomendación: Eliminar uppercase del nombre del usuario. Mantenerlo solo para el folio o identificadores de cuenta. El nombre ya está con font-extrabold para tener jerarquía visual suficiente.
V4
Los iconos de la barra de navegación tienen distintos strokeWidth entre sí
En NavegacionUsuario.tsx: IconoHome usa strokeWidth="2", IconoTraslados y IconoCargaMasiva usan strokeWidth="1.8", IconoCuenta usa strokeWidth="1.8". Esta inconsistencia de 0.2 es visible a 22px cuando los íconos están juntos.
Bajo
Archivo: NavegacionUsuario.tsx:13–58
Recomendación: Unificar todos los íconos de navegación a strokeWidth="1.8" (el valor que visualmente armoniza mejor en el tamaño 22px del contenedor).

10. Rendimiento Percibido y Estados de Carga
P1
El mapa live en dashboard se carga sin indicador de progreso diferenciado
El componente LiveMap cargado dinámicamente muestra un <div role="status">Cargando mapa…</div> sin un placeholder de silueta de mapa. El salto visual del texto al mapa real puede ser disruptivo.
Medio
Archivo: InicioDesktop.tsx:22–25
Recomendación: El loading del mapa debería mostrar un placeholder con un fondo de color neutral + ícono de mapa en gris, del mismo tamaño que el mapa real, para evitar layout shifts.
P2
La foto del conductor se carga de forma diferida pero sin placeholder de avatar durante la espera
En InicioMobile, mientras se resuelve obtenerFotoPerfilConductor, el avatar del conductor muestra el ícono de usuario genérico. No hay un skeleton/shimmer que indique que la imagen está cargando, lo que puede parecer que el conductor "no tiene foto" cuando en realidad está pendiente.
Medio
Archivo: InicioMobile.tsx:156–166
Recomendación: Añadir estado cargandoFoto: boolean que inicie en true mientras se resuelve la promesa. Mostrar un avatar de shimmer durante la carga en lugar del ícono estático.
