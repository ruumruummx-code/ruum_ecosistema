3. Modelo de Seguridad
✓
Content Security Policy con nonce por request (Edge Middleware)
La CSP se genera en middleware.ts con un nonce criptográfico único por request (crypto.randomUUID() → base64). En producción usa strict-dynamic sin unsafe-inline. El nonce se inyecta en los scripts del servidor vía x-nonce header.
Fortaleza
Fuente canónica: @ruum/shared/seguridad exportada como fachada en lib/csp.ts. Corrección ARQ-4 documentada: elimina la doble emisión CSP estática + dinámica que bloqueaba el bundle en producción. Staging emite Content-Security-Policy-Report-Only además de la política estricta para detectar regresiones antes de producción.
✓
CSRF Double-Submit con validación en tiempo constante
Implementación completa en lib/csrf.ts: cookie ruum_csrf_token + header x-csrf-token comparados con compararTiempoConstante() para prevenir ataques de timing. Se valida también Sec-Fetch-Site, Origin y Referer.
Fortaleza
✓
Gate de rol en middleware: conductores bloqueados de rutas de usuario
Corrección FIX C1: un JWT válido de conductor que intente acceder a /viajes/*, /cuenta, etc. recibe un redirect 303 → /403?reason=rol_conductor. La clasificación se delega a @ruum/api/identity para no romper la separación de capas.
Fortaleza
✓
Rate limiting multidimensional con Redis (usuario + IP + dispositivo)
lib/rate-limit-masivos.ts aplica ventanas deslizantes en Redis por tres dimensiones simultáneas. El identificador de dispositivo se hashea antes de almacenarse. También implementado para rutas individuales en lib/csp-rate-limit.ts.
Fortaleza
✓
Headers HTTP defensivos: HSTS, X-Frame-Options, nosniff, Permissions-Policy
Definidos en fuente única lib/csp.ts → headersSeguridadEstaticos(). HSTS solo en producción. Sin X-Powered-By (poweredByHeader: false en next.config). Los headers estáticos son la intersección segura sin nonce; el middleware agrega la CSP dinámica.
Fortaleza
!
La optimización S-5 podría omitir el refresco de sesión en rutas no listadas explícitamente
El middleware solo llama a supabase.auth.getUser() si la ruta está en RUTAS_DEPENDIENTES_DE_SESION. Rutas nuevas añadidas sin actualizar este set recibirían headers CSP correctos pero no refrescarían la sesión/cookie, lo que podría resultar en sesiones expiradas silenciosas.
Atención
Mitigación recomendada: Documentar explícitamente que toda nueva ruta autenticada debe añadirse a ambos sets (RUTAS_PROTEGIDAS_USUARIO y RUTAS_DEPENDIENTES_DE_SESION). Añadir un test de contrato que verifique que ambos sets estén sincronizados.

6. Observabilidad y Trazabilidad Distribuida
✓
Trazado distribuido W3C TraceContext + Sentry en cada request
El middleware genera o propaga traceparent (W3C), sentry-trace, baggage, x-trace-id y x-span-id. Todos los Route Handlers pueden continuar la traza entrante vía trazarRutaApi(). Sentry continueTrace() conecta spans frontend ↔ backend.
Producción-ready
✓
Structured logging con sanitización de PII
lib/logger.ts emite objetos JSON con campos estandarizados (scope, event, level, timestamp). Todos los payloads pasan por sanitizeDetails() de @ruum/api/observability para eliminar datos sensibles antes de registrar.
Fortaleza
✓
Feature flags etiquetados automáticamente en Sentry
Cada evaluación de feature flag llama a Sentry.setTag("ff.{key}", enabled) y Sentry.setTag("ff_stage.{key}", stage), permitiendo correlacionar errores con el anillo de rollout exacto (canary, ring_1_early_adopters, etc.).
Fortaleza
✓
Analytics UX con eventos estructurados
lib/analytics.ts registra eventos de UX (login_visto, login_enviado, login_exitoso, etc.) en cada flujo crítico. Implementado en login, registro, wizard de traslado.
Buena práctica
!
El semáforo de concurrencia PDF no tiene timeout de adquisición documentado
lib/pdf-concurrency-semaphore.ts gestiona concurrencia de generación de PDFs. Sin un timeout máximo de espera, un PDF que falle en generar podría bloquear indefinidamente el semáforo para el siguiente request.
Atención
Recomendación: Añadir un timeout de liberación automática al semáforo (e.g. 30 segundos) y registrar en Sentry cuando se libera por timeout vs por finalización normal.

✓
Suite E2E hermética: dobles de Supabase y Redis locales
El config de Playwright levanta mock-supabase.mjs y mock-redis.mjs como servidores locales. Opt-in a Supabase real vía PLAYWRIGHT_E2E_SUPABASE_REAL=1. Evita dependencia de red externa en CI y credenciales reales.
Fortaleza
✓
Contratos de flujo documentados como archivos .md en lib/
27 documentos de contrato para flujos 6–13 (pagos, KYC, saga de reemplazo, estados huérfanos, retención fiscal, etc.). Cada contrato define precondiciones, postcondiciones y comportamiento en error, usados como referencia para los tests y code reviews.
Documentación
!
LHCI solo cubre 3 rutas públicas (login, registro, privacidad)
Las rutas autenticadas (dashboard, mis-viajes, cuenta) no están cubiertas por Lighthouse CI, por lo que el rendimiento y accesibilidad de las pantallas más usadas no tienen gate automático.
Brecha
Recomendación: Extender lighthouserc.js con al menos una ruta autenticada usando la fixture de sesión existente del setup E2E. Candidatas: /inicio (dashboard) y /mis-viajes.
!
Timeout de 30s en Vitest puede ocultar tests lentos
El testTimeout: 30_000 fue aumentado por un debounce de 300ms en un buscador (RC-09). Este umbral elevado puede ocultar tests genuinamente lentos. 30 tests podrían pasar aunque tarden 25 segundos cada uno sin disparar ninguna alerta.
Atención
Recomendación: Añadir slowTestThreshold: 5000 para reportar tests lentos sin fallarlos, y restaurar el timeout a 15s mientras se investigan los lentos.

8. Patrones de Ingeniería Destacados
  • ✓
    Facade Pattern para Supabase: lib/supabase-browser.ts y lib/supabase-server.ts son fachadas delgadas sobre @ruum/api/next-browser. Permite cambiar la implementación sin tocar los 50+ call sites en la app.
  • ✓
    Reducer puro testeable: nuevoTrasladoReducer y realtimeTrasladosReducer son funciones puras sin efectos secundarios. Optimización Object.is() previene renders redundantes en actualizaciones no-op.
  • ✓
    Saga pattern para flujos de pago: Los contratos pago-individual-saga-contract.md y flujo10-transiciones-policy.ts implementan sagas transaccionales con estados compensatorios para roll-back de operaciones parciales.
  • ✓
    Worker thread para procesamiento masivo: carga-masiva.worker.ts mueve el parsing y validación de Excel/CSV a un worker separado, evitando bloqueo del hilo principal en cargas de cientos de registros.
  • ✓
    Borrador con PII reducido al mínimo: El módulo borrador-traslado.ts excluye explícitamente domicilios precisos, VINs, placas y teléfonos de terceros del almacenamiento local. Las coordenadas se redondean a 2 decimales (~1.1 km de precisión) antes de persistir.
  • ✓
    Feature flags con 6 capas de evaluación: Kill-switch env → Canary allowlist → Consulta remota con caché → Gate de versión → Rollout 100% → Rollout porcentual. Bucketing determinista garantiza que el mismo usuario permanezca en el mismo anillo durante un rollout.
  • ✓
    Capacitor WebView remota (ADR 002): El build de Android apunta a usuario.ruumruum-moviliax.online en producción, no a un bundle local. Las actualizaciones de la web son inmediatas sin publicar en Play Store. WebContents debugging deshabilitado en producción.
  • !
    Hardcoded color values en componentes junto a tokens del Design System: CuentaCliente.tsx, NavegacionUsuario.tsx y MisViajesCliente.tsx mezclan bg-[#0c2340] / text-[#4e5f80] con var(--user-color-*). Hace difícil cambiar la paleta globalmente.
  • !
    Mezcla de estrategias de estilado: CSS Modules en dashboard e InicioDesktop.tsx, Tailwind en CuentaCliente.tsx, y clases BEM propias (user-v2-*) en NavegacionUsuario.tsx. Tres convenciones coexisten sin guía de elección documentada.
